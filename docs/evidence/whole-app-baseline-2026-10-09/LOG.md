## C. Decisions

- **Service root.** `batter::startup::Startup::scoped(supervisor, context, cleanup_budget, |scope| ...)` with `.with_unix_signals("signals").start()`, then `starting.wait().await?` and `running.wait_checked().await?`. Alternatives seen: `Startup::new` (full supervisor access, documented as the lower-level compatibility path), direct `Supervisor::start()`/`run_until` (worker example; caller owns acquisition-failure cleanup), `batter::service::start` (only with the `otlp` feature), `Command` (finite work, not a service). Chose `scoped` because usage.md names it the canonical path and it owns failed-startup cleanup; the smoke run against a closed port confirmed the reserved pool finalizer ran and the process exited 1.
- **Operation budgets.** One `OperationOwner::new(60s)` root bounds initialization; I keep a clone of its context for the startup DDL, migration and catalog sync (`context.run("schema.records", ..)` etc.) because `ProtectedStartupScope` exposes no context accessor. HTTP requests use the boundary's `ResponseConstructionBudget` from settings via `AdmittedRequest::context()`; the create transaction is wrapped as `context.run("records.create", |_| run_atomic(..))` exactly as usage.md describes for the reference command. Single reads/writes use `PgQueryHandle::within(pool, parent, 2s, label, map)`, which clamps to the parent. Worker registration gets its own `OperationOwner::new(10s)` context as the adapter rustdoc shows. Alternatives: `OperationAdmission::admit_root` (for process entry points; the boundary already does this per request), `RootDeadline`, building a root inside a job handler (explicitly forbidden by `job_phases` docs).
- **Pool ownership.** `scope.reserve_cleanup("postgres.pool")?` first, then `RunledgerDatabase::connect_lazy(options, profile, PgPoolOptions)` and `slot.register(move || async move { pool.close().await; Ok(()) })` before returning. Alternative: `batter::sqlx::pool_in(slot, options, connect)` — the documented facade path — but it builds a plain `PgPool`, and `RunledgerDatabase` has deliberately no constructor from an arbitrary pool, so a Runledger consumer cannot use `pool_in`. `register_pool_close(&mut Supervisor, ..)` is unreachable through the protected scope. Profile: `PgSessionProfile::new(login, login, vec!["public"], 30s, 5s)` following the Runledger README quick-start policy; `with_timeouts` was the preferred constructor but requires PostgreSQL 18 transaction timeouts I could not verify locally.
- **Row-plus-job transaction.** `batter::runledger::run_atomic(&database, async |mut scope| { scope.application(insert).await?; scope.record_required_job_enqueue_intent(&intent).await?; Ok(id) })` with `JobEnqueueIntent::new(JobType::new("records.notify"), &payload, "records:<id>:notify")`. The intent phase cannot be reordered after `queue()`, which the type-state enforces. Alternatives: `scope.queue().enqueue_job(&JobEnqueue{..})` (requires an enabled definition at enqueue time; intents are promoted later, which suits an API process that may start before the worker syncs definitions), `run_atomic_with`/`run_atomic_fail_fast_with` (one consumer error through `PgFailurePolicy`; more ceremony than needed for two statements), `batter::sqlx::run_atomic_in` (budget-aware but yields a `PgAtomicScope` without intent methods, so it cannot record the handoff).
- **Worker registration.** `NativeSupervisor::builder(database.pool(), jobs_config)?.with_catalog(&catalog).prepare()?` then `batter::runledger::register_in(scope, "runledger.worker", context, prepared)`. Alternatives: `builder_from_env` (reads `JOBS_*` from the process environment, which conflicts with explicit settings), `.build()` (starts a live supervisor; the adapter's `compile_fail` docs show a live supervisor cannot be registered), `register(&mut Supervisor, ..)` (needs the unprotected supervisor), `with_registry(JobRegistry)` (no definition sync; intents would never promote).
- **Job handler budget.** `job_phases(execution, FINAL_STATE_RESERVE = 500ms)`; the provider sleep runs under `phases.work().child(provider_limit)` and the `notified_at` write under `phases.finalization()` through the `NotifiedLedger` trait. `JobPhasesRejection` is mapped explicitly (`Exhausted|Ended` → timeout, `Unsupported|Reserve` → terminal). Alternatives: `Duration::ZERO` reserve (`split_finalization`; the worker would classify the late write as `job.timeout_exceeded`), `execution.remaining_work_budget(reserve)` with a hand-built timeout, `OperationContext::reserve_finalization` on a fresh root (forbidden: nothing would cancel it when the invocation ends).
- **HTTP assembly.** `HttpBoundary::new(RequestPolicy::new(admission, budget).with_infrastructure_json()).with_liveness(ProbePath::new("/live")).with_readiness(ProbePath::new("/ready"), ReadinessPolicy::new(lifecycle, health)).assemble(GuardedRouter::new().route(..).route(..).with_state(state)).await`, then `register_in(scope, "http", listener)` in production and `in_process()` in tests. Alternatives: `low_level::{request_admission, observe_http, request_scope, operational_http, register_http}` (caller-ordered), `RouteGroup`/`GroupPolicy::browser` (not needed: no browser credentials), `with_rendered_readiness` (empty 200/503 is enough), `register_with_connect_info_in` (no peer needed).
- **Handler inputs.** `State<AppState>`, `AdmittedRequest` (context, correlation id, interruption responder), `Result<Json<CreateRecord>, JsonRejection>` and `Result<Path<Uuid>, PathRejection>` so rejections render in the application envelope with the request id. Alternatives: `Extension<OperationContext>`/`Extension<CorrelationId>` (documented as replaced by `AdmittedRequest`), bare `Json<T>`/`Path<T>` (Axum's default rejection bodies), `Result<AdmittedRequest, AdmittedRequestRejection>` (only needed outside the boundary).
- **Health and readiness.** `HealthMonitor::new(HealthPolicy::new(2s, 3s, 10s, 1s), || SELECT 1 on the shared pool).register_in(scope, "postgres.health")` and `ReadinessPolicy::new(lifecycle, reader)`; liveness is the boundary's empty 200. Alternatives: `batter::sqlx::probe(&pool, &context)` inside the probe (needs an `OperationContext`; the monitor already bounds the whole future, and a fresh root per probe seemed wrong), `ReadinessPolicy::lifecycle_only` (no dependency sampling), `with_condition` (no application state to gate on), foundation `ReadinessEvaluator` directly (the adapter policy wraps it).
- **Settings.** `SettingsSource::from_pairs(std::env::vars_os())` → `select(NAMES, &["RECORDS_"], true)` overlaid on in-memory defaults; `milliseconds` → `ResponseConstructionBudget::new`; `SocketAddr` parse; `PgConnectOptions::from_str` validates `DATABASE_URL` and the text is retained only as `SecretString`; `JobsConfig` is built from the worker id and validated with `validate()` so an invalid worker id fails at load time. Alternatives: `read_file` + `BATTER_ENV_FILE` style dotenv (not required), `JobsConfig::from_env` (implicit environment reads), `bounded_u64` directly.
- **Facade features.** `features = ["axum", "runledger"]`. `runledger` also selects `batter::sqlx` (needed for `PgQueryHandle` and `PgScopeError`) and the native `core/postgres/runtime` namespaces, so no direct Runledger declaration is needed. Not selected: `sqlx` (implied), `metrics`/`otlp`, `runlimit*`, `test-support` (the `in_process()` client and `JobExecution::new` were enough), `runledger-test-support` (Docker-backed; live execution was out of scope).

## D. Documentation gaps

1. **`ProtectedStartupScope` has no operation context.** usage.md says to run "an explicit bounded query or `probe`" after `pool_in` inside `Startup::scoped`, and `probe` takes an `OperationContext`, but the scope exposes only `stage`/`reserve_cleanup`/`registration`. I kept a clone of the startup owner's context before handing it to `Startup::scoped`. Expected guidance in `docs/usage.md` ("Supervising a service") or the `Startup::scoped` rustdoc; the only example that shows `scope.context()` is `owned_pool.rs`, which uses a `CommandScope`.
2. **`pool_in` does not compose with `RunledgerDatabase`.** The facade path for an owned pool (`pool_in`, usage.md and `batter-sqlx` README) yields a plain `PgPool`, while every Runledger atomic/migration API requires a `RunledgerDatabase`, which "has deliberately no constructor from an arbitrary pool". The `RunledgerDatabase::connect_lazy` rustdoc says "reserve pool cleanup before construction and register close before yielding control" but no Batter doc shows that composition; the reference root presumably does, but it is outside the allowed reading set. Expected in `docs/usage.md` or `crates/batter-runledger/README.md`.
3. **`PgScopeError` is not re-exported from `batter::runledger`.** The adapter README says all types needed by `PgFailurePolicy` handlers are re-exported "here", and `batter::runledger` does re-export `PgScopeFailure`, `PgScopeLoss`, `PgTransactionError`, but `scope.application(..)` returns `PgScopeError<E>`, which lives only at `batter::sqlx::PgScopeError` (and in the native namespace). First compile error of this build. Expected in `crates/batter-runledger/src/lib.rs` re-export list.
4. **No budget-aware Runledger `run_atomic`.** `batter::sqlx` has `run_atomic_in(&pool, &context, name, ..)` and `run_atomic_profiled_in`, but the Runledger runner (the only one with `PgIntentScope`) has no `_in` variant; usage.md says to "pass one operation budget around `run_atomic`", which I read as wrapping it in `context.run(..)`. A sentence in `crates/batter-runledger/README.md` confirming that wrapping is the intended composition (and that the dropped future retires the connection) would remove the guess.
5. **`AdmittedRequest::correlation_id()` returns a reference.** The `render_infrastructure_failure(.., Some(admitted.correlation_id()))` example compiles because the function takes `Option<&CorrelationId>`, but nothing states the return type, so my helper taking it by value failed to compile. Minor; expected in the `AdmittedRequest` rustdoc summary.
6. **`PgNativeQuery` does not accept `sqlx::query_as`.** The README lists `Query`, `Map` and `QueryScalar` ("including `query_as!` results"), which is correct for the macro, but the runtime `sqlx::query_as::<_, T>(..)` returns `QueryAs`, which is not accepted; I used `query(..).try_map(..)`. Worth a sentence in `crates/batter-sqlx/README.md` under the single-query helpers, since the task mandates runtime query APIs.
7. **Job handler testability.** The native `JobExecution::new(&context, &services)` plus a custom `JobExecutionServices` owning a `JobInvocationOwner` is the only in-process way to drive a `JobExecutionHandler`, and the recipe is only in the `JobExecutionServices::invocation` rustdoc (`runledger-core/src/jobs/execution.rs`). `batter::runledger`'s module docs and `docs/testing.md` were where I expected a "test a handler without a worker" note; the facade `test-support` feature does not cover it.
8. **`JobInvocationOwner::end()` is `#[must_use]`.** Not mentioned in the services rustdoc example (which never calls `end`); clippy `-D warnings` flagged the dropped `JobInvocationHookPanics`. Asserting it is empty is the right test, so a line in that rustdoc would help.
9. **Definition sync is required for intent promotion.** llms.txt and the README say promotion happens only for "registered, enabled types", but the Batter-side docs for `register_in` only say "schema/catalog synchronization ... belong to owned application startup before registration" without naming `JobCatalog::sync_definitions`. I found it in the Runledger README quick start. A pointer in `crates/batter-runledger/README.md` would save a round trip.
10. **Budget sizes are only illustrative.** `docs/operations.md` is explicit that the example budgets are not recommendations, but there is no guidance on relating `ShutdownBudget` drain time to the Runledger worker's `lease_ttl_seconds`/handler timeouts and the adapter's "native graceful and abort/join allowances come from the process budget's drain and cancellation phases". I chose 10 s drain against a 30 s job timeout and left it as application policy.
11. **`with_timeouts` vs `new` on PgSessionProfile.** The adapter README says to prefer `with_timeouts` (four server timeouts); the Runledger quick start uses `new`. Without a PostgreSQL 18 server to verify `transaction_timeout` support I used `new`; the docs do not say which is the Batter-consumer default.
