# batter-at-rest envelope format version 1

This document normatively defines version 1. All integers are unsigned and big-endian. Every length counts bytes, not characters. Decoders reject truncation, noncanonical fixed lengths, values above the documented limits, unknown versions, inconsistent nested lengths, and trailing data.

Version 1 fixes AES-256-GCM, HKDF-SHA256, 32-byte master and data keys, 12-byte nonces, and 16-byte authentication tags. A future algorithm or incompatible encoding requires a new format version; version 1 has no algorithm selector.

## Limits

- Key ID: 1–128 case-sensitive ASCII bytes from `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, or `-`.
- Canonical context labels: 1–64 lowercase ASCII bytes from `a-z`, `0-9`, `.`, `_`, `:`, or `-`.
- Owner, resource, or tenant binding component: 1–128 opaque bytes.
- Encoded context: at most 512 bytes.
- Encoded envelope header: at most 256 bytes.
- Plaintext: at most 67,108,864 bytes (64 MiB).
- Ciphertext body: plaintext length plus exactly 16 bytes.

## Canonical context

The context codec begins with `codec_version:u8 = 1` and `binding_kind:u8`. Every following component is `length:u16 || bytes`.

For `binding_kind = 1` (row), components are namespace, purpose, owner, resource, and payload schema in that order. For `binding_kind = 2` (tenant-scoped bearer token), components are namespace, purpose, tenant, and payload schema. There is no public raw-context constructor.

Values using one tenant-token namespace, purpose, tenant, and payload schema share the same context and are intentionally interchangeable at the cryptographic layer. Consumers that require per-token or per-row isolation must use a row binding with the real resource identity instead.

Namespace, purpose, and payload schema are canonical labels. Owner, resource, and tenant are application-supplied canonical identity bytes; the library preserves them exactly and only length-frames them. A row caller must pass the real owner and resource identity. A tenant-token caller does not invent a row ID.

Payload schema is application data and is distinct from format version. Encryption-key ID is wrapper metadata and is distinct from both. Stable equality/identity key IDs are not part of this format.

## ContentDescriptor

The independently encoded immutable descriptor is:

| Field | Size | Value |
| --- | ---: | --- |
| format version | 1 | `1` |
| payload nonce length | 1 | `12` |
| payload nonce | 12 | OS-generated bytes |

The encoded descriptor is exactly 14 bytes.

## WrappedKey

The independently encoded rotatable wrapper is:

| Field | Size | Value |
| --- | ---: | --- |
| wrapping-key ID length | 1 | `1..=128` |
| wrapping-key ID | variable | validated safe ASCII |
| wrapping nonce length | 1 | `12` |
| wrapping nonce | 12 | OS-generated bytes |
| encrypted data-key length | 2 | `48` |
| encrypted data key | 48 | 32 ciphertext bytes followed by 16-byte tag |

The sole format version lives in `ContentDescriptor`; a `WrappedKey` is interpreted only with its descriptor. This keeps split SQL storage from persisting two version authorities that can disagree.

## Envelope and SealedPayload

The encoded envelope header is:

| Field | Size | Value |
| --- | ---: | --- |
| magic | 4 | ASCII `ATRE` |
| descriptor length | 2 | `14` |
| descriptor | variable | canonical `ContentDescriptor` |
| wrapped-key length | 2 | canonical encoded wrapper length |
| wrapped key | variable | canonical `WrappedKey` |

The encoded composite sealed payload is:

| Field | Size | Value |
| --- | ---: | --- |
| magic | 4 | ASCII `ATRS` |
| envelope length | 2 | canonical encoded envelope length |
| envelope | variable | canonical `Envelope` |
| body length | 4 | ciphertext body length |
| body | variable | payload ciphertext followed by 16-byte tag |

Storage adapters may persist the descriptor, wrapped key, and body separately or use the composite bytes. They must decode each persisted part through this crate. Physical table, column, bucket, or object-key names are not cryptographic inputs.

## HKDF and authenticated data

The wrapping key is `HKDF-SHA256(master_key, salt, info)` expanded to 32 bytes. The fixed salt is the ASCII bytes `at-rest:envelope:v1:wrapping-key:salt`. The info value is ASCII magic `ATRK`, then `format_version:u8 = 1`, then `role:u8 = 3`, then namespace and purpose as `length:u16 || bytes`. The master selected by the wrapping-key ID is the HKDF input keying material.

Payload AAD is ASCII magic `ATRA`, `role:u8 = 1`, `format_version:u8 = 1`, and the complete context as `length:u16 || bytes`. It excludes the wrapping-key ID and physical storage location, so rewrap and storage movement preserve the body.

Wrapping AAD is ASCII magic `ATRA`, `role:u8 = 2`, `format_version:u8 = 1`, the wrapping-key ID as `length:u16 || bytes`, the 12-byte payload nonce as `length:u16 || bytes`, and the complete context as `length:u16 || bytes`. Its distinct role prevents a valid body/tag from being interpreted as a wrapped key or vice versa.

Seal generates a random data key, payload nonce, and wrapping nonce. Open authenticates the wrapper before authenticating the body and returns plaintext only after both succeed. Rewrap authenticates the wrapper and context, then encrypts the same data key under the current wrapping key with a fresh wrapping nonce. It returns only `WrappedKey` metadata and deliberately does not inspect or attest to an unread body. If the stored wrapping-key ID already is current, rewrap still authenticates it and returns the exact existing wrapper.

A replacement wrapper is valid only with the exact descriptor supplied to rewrap. A storage adapter must persist it with a compare-and-swap condition on the descriptor bytes, complete envelope, or an equivalent row revision that covers them. If the condition fails because a concurrent writer resealed the payload, the adapter must discard the replacement and retry from a fresh read; it must never overwrite the new wrapper with metadata derived from an older descriptor.

Random 96-bit wrapping nonces require fewer than `2^32` wrapper encryptions under any one derived wrapping key. The counter is shared by every process using the same master-key, namespace, and purpose combination, including distinct IDs that alias identical master bytes. Seal and different-key rewrap consume one invocation; same-key rewrap does not. This stateless crate does not enforce the aggregate count; the consuming key-configuration and provisioning owner must enforce a conservative key lifetime or traffic ceiling and rotate before the limit. Rewrap preserves the data key and body, so it is not sufficient after master-key compromise; compromise recovery requires full open-and-reseal plus treatment of historical wrapper copies.

A wrapping-key ID is a permanent, case-sensitive binding to one exact master-key value. It must never be rebound or reused for different bytes. Consumers rotate by adding a fresh ID, rewrapping references, auditing live and recoverable historical wrappers, and then retiring the old binding.
