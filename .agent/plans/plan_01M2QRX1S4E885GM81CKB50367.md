# Renew replay retention and own live listener binding

This task-local ExecPlan belongs to Bead `batter-8q8.5`. It follows the
2026-09-17 comprehensive review and the ADR-010 recurring-defect assessment.
Earlier completed plans remain historical evidence and are not rewritten.

## Outcome

Fresh provider dispatch after authoritative absence receives a fresh retention
window, and every live probe uses the TCP address actually selected and owned by
its production child. Completion requires focused regressions plus the repository's
required final verification on unchanged current-version contracts.

## Scope

In scope: the reference worker transition, its live regression, port-zero address
reporting, the private production-child harness, contracts, evidence, and the
owning Bead. Non-goals: Batter/adapter/Runledger APIs, schema or protocol changes,
backfill, rolling compatibility, publication, deployment, staging, or commits.

## Surprises & Discoveries

- The stale deadline is not caused by the retained-state architecture itself. The
  worker correctly reconciles before replay, but `ReconcileOutcome::Absent` is
  collapsed into `None`; dispatch then infers authorization from the unchanged
  `ReconcileNeeded` state and skips the only timestamp-setting transition.
- The shared `reserved_address` helper drops its listener before every production
  child starts. The address is therefore only a guess. Retrying would reduce the
  symptom but would not establish ownership.
- The production runtime already accepts port zero. Reporting the address selected
  by that child is the smallest way to preserve the real executable while removing
  the time-of-check/time-of-use gap.
- The initial focused live run failed because the new generic scenario reused an
  existing fixture UUID (`0x418`), not because of the production change. Moving it
  to unused `0x41b` made the exact outcome probe pass; PostgreSQL's unique-key
  diagnostic supplied the evidence without weakening redaction in the test API.
- File-budget enforcement required the new replay scenario and listener protocol
  to live in focused child modules. This preserved the existing 800-line owners
  and made the targeted Jig file-budget check pass.

## Decisions and design

### D-01 — Keep the remedy reference-local

- Status: accepted
- Context: Batter already supplies bounded operations/admission and Runledger
  supplies lease fencing. Provider retention semantics and executable fixture
  launch are application/test concerns.
- Choice: change only the reference worker, its production-root address report,
  live harness, contracts, evidence, and tracker state.
- Why: no repeated caller reconstruction of a Batter-owned lifecycle exists here.
- Alternatives: a foundation/provider abstraction would reverse dependency
  ownership; retrying bind failures would retain the race.

### D-02 — Represent proven absence explicitly

- Status: accepted
- Choice: return an explicit reconciliation result and carry a typed dispatch
  origin into the remote-effect boundary. Initial dispatch and replay after
  authoritative absence use distinct SQL transitions, both lease/source-state
  fenced. The replay transition resets `dispatch_possible_at` and
  `resolve_before` only after absence and immediately before POST polling.
- Why: `ReconcileNeeded` describes durable uncertainty but cannot also prove that
  the current invocation performed an authoritative absence lookup.

### D-03 — Let the child own and report dynamic listener selection

- Status: accepted
- Choice: worker children use `127.0.0.1:0`; after the real runtime binds, it
  emits one bounded, parseable non-secret address line. The process owner waits
  for and validates that line, retains the address with the child, and permits
  exactly that line at settlement.
- Why: the process that binds is the only authority for the selected port. This
  removes the race without adding fd-passing machinery or a test-only production
  branch.
- Revisit when: the reference executable gains a structured control socket or
  inherited-listener contract.

## Context and orientation

`examples/reference-service/src/delivery/worker.rs` owns reconciliation and the
remote-effect boundary; `delivery/worker/state.rs` owns lease-fenced SQL writes.
`tests/support/startup_process.rs` owns real child processes, and
`tests/support/provider_effects.rs` plus `production_root.rs` consume their bound
addresses. `runtime.rs` owns the actual TCP bind. Current-version runnability is
the only compatibility target: no migration backfill or rolling-version behavior
is in scope.

## Risks and open decisions

- Risk: address reporting could weaken the process-output oracle. Mitigation:
  accept exactly one parsed loopback address line for running port-zero children;
  retain empty stderr, capture bounds, panic checks, and secret scanning.
- Risk: renewing too early could extend unresolved uncertainty without provider
  evidence. Mitigation: only the explicit authoritative-absence result selects
  the renewal SQL transition, immediately before POST polling.
- Open decisions: none. Both changes are reversible and reference-local.

## Validation and acceptance

Acceptance requires the reviewed near-expiry scenario to fail against the old
control flow and pass after renewal, all real child launches to use child-selected
addresses, no unexpected stdout/stderr or secret disclosure, unchanged current-
version schema/protocol identities, and all repository-required checks above.

## Idempotence and recovery

The code changes are repeatable and do not mutate deployed data. Live fixtures
use disposable databases and explicitly settled child processes. Preserve the
existing dirty worktree and index; do not stage, commit, publish, or deploy.

## Interfaces and dependencies

No Batter, adapter, Runledger, provider wire-protocol, schema, or dependency
change is planned. The only new executable observation is a generic listener
address line emitted when the configured port is zero and consumed by the private
process harness.
