# Security and trust boundaries

Batter has not had a dedicated security audit.
Authentication, authorization, and related controls remain application-owned;
do not treat Batter itself as a security control. Application-specific hardening
still belongs with the consumer; see [backlog access](docs/roadmap.md).

## Boundaries that remain application-owned

Authentication, authorization, trusted proxy interpretation, tenant isolation,
TLS, CSRF/CORS policy, body/socket/queue limits, secret loading, migration policy,
and external-effect idempotency are outside Batter. A readiness gate is not an
authorization gate. A concurrency permit is not a per-user rate limit. A timeout
is not rollback or permission to replay a mutation.

Two library-built clients are exceptions. The `batter-otlp` exporter's private
transport uses reqwest 0.13.5 with explicit rustls *ring* configuration and
bundled WebPKI roots, and bounds its payload and response bodies. It installs
no global provider, fixes HTTP/1.1 and disables redirects, proxies, retries and
decompression. The reference provider uses the same TLS policy. The experimental outbound
exchange (`batter-outbound-http`, also `batter::outbound_http`) builds its own client
too: the package fixes its rustls configuration, with the *ring* provider passed explicitly,
TLS 1.3 and 1.2 only and, for an HTTPS origin, the operating system's
certificate verifier; `https_only` for an HTTPS origin, as defence in depth
behind `Origin::https`; an ALPN list of `http/1.1` only; and a required
`ResponseLimit` on every response body. The application still owns the trust
store and its environment, such as `SSL_CERT_FILE` and `SSL_CERT_DIR` on Linux,
any process-default crypto provider that other crates in its graph need,
certificate pinning, which the package does not offer, and every egress or
destination policy: `Origin::https` accepts any HTTPS host the application
passes, IP literals included. The package adds no instrumentation of its own,
but its dependencies log destination identities (source-inspected): reqwest the
host at debug level, hyper-util the origin's authority and the socket addresses
it connects to at debug and trace level, and rustls-platform-verifier a failed
certificate verification at error level, with the expected and presented names
for a name mismatch. When another crate in the application's graph enables
rustls's `logging` feature, a default of rustls, tokio-rustls and
hyper-rustls, rustls also logs the server name at debug level and the
ClientHello and the server certificate chain at trace level. None of them
carries an exchange's path, query, header value or body. The application's
logger or subscriber configuration owns filtering the `reqwest`,
`hyper_util`, `rustls_platform_verifier` and `rustls` targets. No outbound-exchange
test verifies a certificate. Its local macOS checks in `batter-8e8r` cover
transport behavior; the separate OTLP/reference migration in `batter-7oob`
tests self-signed certificate rejection and an explicitly trusting control.

Bulkhead does not bound its waiter count or request memory. HTTP deadlines stop
at response construction and do not protect streaming sessions or every slow
upload/connection path. Runtime-thread blocking can defeat cooperative timers.

Finite process admission separately bounds queued plus executing tasks, not
their captured payload sizes. Its task-level error channel triggers process
drain; expected user/business rejection must remain a successful task value.
Custom HTTP renderers are application code and receive request parts: they must
not echo raw headers, URLs, or sources. The example's private request-ID extension
is generated by outer middleware; it does not establish proxy/header trust.

## Diagnostics

Batter's own tracing fields avoid automatic raw errors, subjects, URLs, request
bodies, and panic payloads. Internal reports retain original errors; Debug/source
inspection or an application's logs can expose them. Do not serialize reports
as HTTP responses. Use explicit sanitized domain mappings and low-cardinality
metric labels. Operation names must remain developer-controlled constants.
`SecretString` and `RedactedError` redact Display/Debug; `expose_secret` and
`Error::source` remain trusted inspection. Settings do not erase memory or
sanitize third-party logs.

Rust's default panic hook prints payloads to stderr before a JoinError is
observed. Batter never installs, takes or replaces a global hook. An
application root that installs `redacting_panic_hook` as the first statement of
`main` prints each panic's location instead of its payload, but Rust still
prints a payload itself in a child that `std::process::Command` forks, a wrapper
or later hook that formats `PanicHookInfo` prints it again, and formatting a
retained JoinError discloses a string payload. Tracing hygiene is not whole-process secret
redaction. Never put secrets in panic messages.

## Dependencies and publishing

The local source forbids unsafe code in all four library crate roots; that is not an audit
of transitive dependencies or proof of logical cancellation safety. Resolve and
review Cargo.lock, run your dependency advisory/license checks, and evaluate
all optional features on the actual target platform. CI actions are separate
supply-chain dependencies that also require review.

Release-package manifests target crates.io, but that does not establish that any
upload or registry-name reservation completed. Before publication, establish an
owner-controlled private vulnerability reporting channel rather than inventing
a maintainer email address here.
